# Code Reviewer 代码审查规范

本规范整合自《修改软件的艺术》《代码整洁之道》《代码的未来》，为代码审查者提供统一的审查标准。

## 审查的核心目标

代码审查不仅仅是找 bug，而是：

1. **确保代码正确** — 逻辑正确，功能实现符合需求
2. **确保代码可维护** — 清晰、简洁、易于修改
3. **确保代码安全** — 无安全漏洞
4. **确保代码高效** — 性能满足要求
5. **知识共享** — 团队成员相互学习

> 代码审查是「童子军规则」的最后一道防线。

## 审查流程

```
1. 理解需求 → 阅读 PR 描述和任务描述
2. 快速浏览 → 了解整体结构和改动范围
3. 逐文件审查 → 按优先级检查
4. 汇总反馈 → 按严重程度分类
5. 给出结论 → Approve / Request Changes / Comment
```

## 阻塞性问题 (🔴 Must Fix)

出现以下问题时，必须阻止合并：

### 功能性
- [ ] 逻辑错误导致功能不正确
- [ ] 边界条件未处理
- [ ] 破坏已有功能（回归）
- [ ] API 契约被破坏

### 安全性
- [ ] SQL 注入 / XSS / 命令注入
- [ ] 权限绕过
- [ ] 敏感数据泄露
- [ ] 认证/授权缺陷

### 稳定性
- [ ] 内存泄漏
- [ ] 未捕获的异常导致崩溃
- [ ] 线程安全问题
- [ ] 资源未正确释放

## 建议性问题 (🟡 Should Fix)

以下问题建议修复，可以合并但不推荐：

### 可维护性
- [ ] 重复代码（违反 DRY）
- [ ] 过长函数/类
- [ ] 命名不清晰
- [ ] 缺少必要的注释

### 代码质量
- [ ] 违反 SOLID 原则
- [ ] 错误处理不当
- [ ] 硬编码常量
- [ ] 类型安全问题

### 性能
- [ ] N+1 查询
- [ ] 不必要的重渲染/重复计算
- [ ] 内存浪费

## 优化性问题 (💭 Nit)

以下问题可以忽略或作为建议：

- [ ] 代码风格偏好（已有规范除外）
- [ ] 可以进一步简化的代码
- [ ] 命名可以更优雅
- [ ] 可以抽取的辅助方法

## Clean Code 检查清单

### 命名
- [ ] 变量名揭示意图（不需要注释解释）
- [ ] 函数名描述行为（动词）
- [ ] 类名是名词
- [ ] 常量名表达含义
- [ ] 无误导性命名

### 函数
- [ ] 短小（不超过 20 行）
- [ ] 只做一件事
- [ ] 参数不超过 3 个
- [ ] 无副作用或副作用明确
- [ ] 无 boolean flag 参数

### 类
- [ ] 单一职责（SRP）
- [ ] 内聚（使用大部分实例变量）
- [ ] 依赖抽象而非具体
- [ ] 方法组织有序（公共在上，私有在下）

### 注释
- [ ] 代码自解释
- [ ] 注释解释「为什么」而非「是什么」
- [ ] 无过时注释
- [ ] 无被注释掉的代码

### 测试
- [ ] 有单元测试覆盖核心逻辑
- [ ] 测试命名描述性
- [ ] 测试独立性
- [ ] 测试覆盖边界条件

## 代码气味

识别需要重构的问题：

| 气味 | 描述 | 解决方案 |
|------|------|----------|
| 重复代码 | 两处或多处相同的逻辑 | 提取为公共函数 |
| 过长函数 | 超过 20 行 | 拆分为多个函数 |
| 过大类 | 超过 300 行 | 拆分职责 |
| 过深嵌套 | 超过 3 层 | 卫语句提早返回 |
| 参数过多 | 超过 3 个 | 参数对象模式 |
| 霰弹式修改 | 一个改动影响多处 | 提取抽象 |
| 依恋情结 | 方法过多操作其他类 | 移动方法或数据 |
| 夸夸其谈的未来 | 过早抽象 | YAGNI |

## 重构技法参考 (Martin Fowler)

识别到坏味道后，推荐使用以下重构技法：

| 坏味道 | 推荐重构 |
|--------|----------|
| 重复代码 | 提取函数、提取超类、模板方法 |
| 过长函数 | 提取函数、替换算法、卫语句 |
| 过大类 | 提取类、提取接口 |
| 过长参数列表 | 提取参数对象、保持对象 |
| Switch 惊悚 | 替换为多态、策略模式 |
| 数据泥团 | 提取参数对象、保持对象 |
| 基本类型偏执 | 以对象取代基本类型 |
| 依恋情结 | 搬移函数、提取类 |
| 散弹式修改 | 移动函数、合并类 |

## 审查话术示例

### 阻塞性
> 「第 42-45 行存在 SQL 注入风险。使用 `PreparedStatement` 参数化查询，不要拼接字符串。」

### 建议性
> 「建议将 `processUserData` 方法拆分为 `getUser`, `updateUser`, `deleteUser` 三个方法，使职责更清晰。」

### 优化性
> 「这个变量名 `tmp` 可以改成 `tempFile` 或具体含义，使代码更自解释。」

### 表扬
> 「这里使用策略模式处理不同支付方式很漂亮！👍」
> 「这个提取的 `useDebounce` Hook 设计得很好，可以复用。」

## 童子军规则

每次审查时，至少做一件小事让代码更干净：

1. 指出一个命名不清的地方
2. 发现并要求消除一个小重复
3. 建议简化一个复杂表达式
4. 要求添加一个遗漏的测试
